# Сборка, окружения и эксплуатация

## Изменение: один лендинг

Актуальное решение — [requirements](../requirements.md) и [frontend](../frontend/architecture.md): один index.html, секции home → the-app → why-luni → support → plans → checkout → account по PNG 01–07. Старые отдельные страницы/entries относятся к прежней реализации и подлежат объединению. Checkout/Account остаются demo внутри документа. Metadata, canonical и robots задаются всему HTML; отдельный noindex якорю невозможен. Выбор plan обновляет сводку в одном документе, прямая ссылка допустима как ?plan=monthly#checkout. Миграция и её проверки не подтверждены.

Ниже сохранены схемы и инфраструктурные детали; требования об отдельных HTML заменены решением выше.

Статус: целевая схема. Пользователь выбрал собственный сервер с SSH / Nginx; [pipeline и инструкция настройки](github-actions-deployment.md) подготовлены заранее. Домен и параметры сервера ещё не заданы, код frontend отсутствует, фактическое развертывание не выполнено.
Объём архитектуры охватывает шесть экранов; состав конкретной первой итерации ещё согласуется в docs/task-002.md. Формулировки о первой реализации ниже описывают целевой вариант полного прототипа, а не принятое изменение объёма FRONT-001.


## Окружения

| Окружение | Источник данных | Публикация / данные |
|---|---|---|
| local | Demo fixtures | Dev server, локальный доступ |
| preview | Demo; позднее sandbox API | Изолированный адрес, noindex, без production-секретов |
| production первого прототипа | Явный demo | Только если согласована публикация прототипа; checkout/account обозначены |
| production live | Реальный API | После коммерческой и интеграционной приёмки |

Noindex не ограничивает доступ. Если preview должен быть закрытым, доступ ограничивается средствами хостинга. Переключение demo/live — конфигурация сборки; ошибка live API не включает demo автоматически.

## Публичная конфигурация

Проектные ключи: APP_ENV, DATA_MODE, BASE_PATH, PUBLIC_SITE_URL, PUBLIC_API_BASE_URL. Они доступны пользователю после сборки и не содержат секретов. Названия и способ чтения закрепляются при реализации. Не передавать весь process.env в браузер.

Для каждого окружения проверить завершающие slash, формирование ссылок и прямые запросы HTML. PUBLIC_SITE_URL задаётся только для известного домена. Demo checkout/account не включаются в индексируемый sitemap.

## Pipeline

1. Получить фиксированную версию исходников.
2. Установить закреплённую версию Node/npm и зависимости через npm ci.
3. Проверить схемы контента, ссылки на ресурсы, lint.
4. Собрать dev/prod и проверить наличие шести HTML.
5. Раздать production через HTTP; выполнить сценарии и сбор ошибок ресурсов/консоли.
6. Сохранить артефакт build/prod, metadata сборки и QA-отчёт.
7. Разместить тот же проверенный артефакт в выбранном окружении.
8. Проверить URL страниц, base path, ресурсы, CTA и корректный demo/live режим после публикации.

Публикация не считается частью текущей задачи описания архитектуры. Автоматический deploy Nordel не переносится без настройки окружения LuniVPN.

## Статическая доставка

Хостинг должен отдавать отдельные HTML, корректные MIME и 404 для неизвестных страниц. SPA fallback не требуется. HTML обновляется с ревалидацией; хешированные CSS/JS/изображения можно кешировать надолго. Старые ресурсы не удаляются так рано, чтобы уже открытая HTML-страница ссылалась на исчезнувшие файлы.

Ресурсы из src/assets проходят сборщик; public копируется по явному списку. docs, fixtures, source maps с нежелательным содержимым и .env не публикуются автоматически. Ссылки и asset path проверяются как в корне домена, так и под BASE_PATH.

HTTPS, заголовки безопасности и CSP настраиваются на хостинге. Политика CSP учитывает фактический платёжный SDK только после его выбора; произвольные внешние scripts не разрешаются заранее.

## Этап C

Браузер обращается к /api/v1 через reverse proxy либо согласованный API origin. Backend имеет собственный runtime и секреты, БД и миграции. Среда сервера не зависит от Node, используемого только для сборки сайта.

До запуска описать отдельно:
- deploy и rollback frontend/backend, совместимость версий API;
- миграции с обратной совместимостью, условия отказа от отката;
- liveness процесса и readiness зависимостей;
- резервное копирование, восстановление и ответственного за проверку;
- webhook ingress, повторную обработку и сверку платежей;
- наблюдаемость, алерты и процедуру инцидента.

Для Account/Billing конкретные Dockerfile и команды рестарта появляются после выбора технологий. Для вишлиста локальный Compose уже описан отдельно в требованиях. Наличие этого документа не означает существование серверов или backup.

## Наблюдаемость и восстановление

Для статики: доступность URL, HTTP-ошибки, ошибки загрузки ресурсов и размер артефакта. Клиентский сбор ошибок и аналитика — отдельное решение с минимизацией данных. Для backend: requestId, код ответа, задержка, сбои зависимостей, очередь/ошибки событий платежей; без реквизитов и секретов.

Rollback статики — возврат предыдущего неизменяемого артефакта. Перед live rollback проверить совместимость API и схему данных. Критерии RPO/RTO и SLA задаются владельцем сервиса до production, а не считаются известными.

## Отдельная доставка вишлиста

Контур W: site + PHP bot + ngrok + volume wishlist для локального стенда. [Требования к Compose и запуску](../backend/docker-compose.md) определяют переменные, порты, регистрацию webhook, сохранность и backup. Существующий SSH/Nginx pipeline сайта сохраняется; он не развёртывает бота и не управляет его webhook. Для production нужен отдельный выпуск PHP-сервиса, HTTPS ingress и хранилище вне каталогов frontend-релизов. ngrok и встроенный php -S остаются локальными инструментами.
