# Backend и внешние интеграции LuniVPN

Статус: backend вишлиста включён в план реализации по запросу пользователя; код ещё не перенесён. Для него выбран образец Nordel: PHP 8.4, webhook, JSON и Docker Compose. Account/Billing ниже относятся к отдельному будущему этапу C.

Проект операций и ошибок: [API-контракты](api-contracts.md). Сущности: [модель данных](../architecture/data-model.md). Общая схема эксплуатации: [окружения и доставка](../architecture/deployment.md). Эти документы описывают будущее решение; окончательные технологии и провайдеры остаются открытыми.

## Вишлист — ближайшая реализация

Основной документ: [требования WL-01–14](wishlist-requirements.md). Дополнения: [окружение и запуск](docker-compose.md), [приёмка](wishlist-validation.md), [task-012](../task-012.md). Сценарий: сайт → Telegram → /start → запись пользователя → приветствие. Собственного REST API регистрации для браузера не требуется. Пользователь вишлиста не является аккаунтом LuniVPN.

## Границы систем

| Контур | Ответственность | Что нужно определить |
|---|---|---|
| Wishlist backend | PHP webhook, Telegram, JSON-хранилище | Собственный бот, секреты, точка входа и production origin |
| Публичный frontend | Показ продукта, планов и поддержки | Контент и маршруты |
| Account API | Сессия, профиль, доступ к данным пользователя | Способ входа, logout, восстановление, ошибки |
| Billing API | Каталог планов, checkout, подписка, история | Провайдер, суммы, статусы, продление/отмена |
| Платёжный провайдер | Платёжная форма и обработка оплаты | Hosted checkout либо SDK; доступные методы |
| Support | Статьи, поиск, обращения | Статический корпус либо API, канал контакта |
| VPN-инфраструктура | Подключение, локации, протоколы, kill switch | Отдельный проект и контракт, не frontend лендинга |

## Обязательные контракты до интеграции

1. **Каталог:** устойчивый planId, название, период, валюта, цена в минимальных денежных единицах, доступность, правила отображения итоговой суммы.
2. **Checkout:** вход planId и необходимые данные заказа; выход идентификатор сессии и следующий шаг. Сервер проверяет план и сумму; значения из URL/браузера не являются источником цены.
3. **Платёжный статус:** pending/succeeded/failed/cancelled/expired; событие провайдера проверяется и обрабатывается повторно безопасно. Возврат на success URL сам по себе не активирует подписку.
4. **Подписка:** статус, план, дата/условия продления, действие отмены и последствия. Эти правила задаёт продукт.
5. **Профиль:** собственные данные пользователя, разрешённые изменения и повторная проверка личности для чувствительных действий.
6. **Ошибки:** стабильный код, безопасное сообщение, retryable; правила timeout/retry, защиты от повторного submit и недоступности API.
7. **Авторизация:** серверная проверка доступа к каждому объекту; logout завершает сессию. В документации определить cookies/token, CSRF/CORS и срок жизни в зависимости от выбранной схемы.

Точные URL, HTTP-методы, схемы, примеры и коды ошибок закрепить в спецификации API после выбора архитектуры. Примеры содержат только синтетические данные.

## Платёжная форма и demo

В прототипе не принимать реальные номера карт и CVC: использовать явно обозначенные макеты или sandbox выбранного провайдера. Для реальной оплаты предпочтительно вынести ввод реквизитов в hosted checkout/защищённые поля провайдера; архитектурное решение фиксируется отдельно. Не сохранять реквизиты в localStorage, логах или аналитике.

Desktop и mobile показывают один заказ и один каталог; расхождения Premium Plan / Automatic Plan / Monthly / Yearly разрешаются D03/D04. Показанный в концепте PayPal не подтверждает его поддержку.

## Требования к эксплуатации и проверке

После выбора backend подготовить status.md и deployment.md: фактические сервисы, конфигурация без секретов, запуск, health/readiness, миграции, резервное копирование и проверка восстановления, rollback, наблюдаемость и окружения.

Проверить: недоступный API, истёкшую сессию, отказ доступа к чужим данным, двойной submit, отмену/ошибку платежа, повторное/задержанное событие провайдера и восстановление после сбоя. Sandbox-проверки и реальный сквозной прогон описывать раздельно.

Telegram-вишлист включён в task-012. JSON на одном узле и ngrok предназначены для локального MVP; production требует отдельного HTTP runtime/HTTPS ingress и проверки восстановления по docker-compose.md.
